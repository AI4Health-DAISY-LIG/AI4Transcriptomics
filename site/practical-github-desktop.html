Git without the terminal: GitHub Desktop

The Git side of the practical sessions, with buttons. You fork the course repository, commit and push your work, open the pull request that carries your submission, ask in Issues and review a peer.

0. Before you start

The practical sessions run in the course repository AI4Health-DAISY-LIG/AI4Transcriptomics_AI4OH_2026 ↗. Its README states the rules, the grading and the deadlines, and it prevails over this page. This tutorial shows how to do each Git operation it asks for with GitHub Desktop, a Git client for Windows and macOS. Each button corresponds to a command of Course 03 · Git Best Practices; the table at the end gives the mapping.

Three copies of one repository

You have no write access to the course repository, so you work through a fork. A fork keeps its link to the repository it comes from: GitHub shows "forked from", tells you how many commits you are behind, and syncs the two in one click. Your pull request carries that origin with it, so each line of your submission can be traced to you and to a commit.

You commit in your clone and push to your fork. One pull request, opened early, shows your fork to the course repository until the deadline. It targets the branch named after your GitHub handle, which the instructor creates for you. Nobody merges it during the practical: its state at the deadline is what is graded.

The course repository is public: your fork, your code and your comments are visible to anyone. You may use a GitHub account that does not show your real name.

Learning objectives served

  • Reproducibility. Each state of your analysis is a commit that another person can pull and rerun.
  • Provenance, transparency and collaborative translational science. Commits, issues and reviews record who did what, when and why.

Before the first practical

  • A GitHub account.
  • Your GitHub handle sent through the set-up form on UNESS. The instructor then creates the branch named after your handle.
  • uv installed ↗.

1. Install and sign in

Download GitHub Desktop from desktop.github.com ↗ and install it.

Open it and sign in with your GitHub account: File → Options → Accounts on Windows, GitHub Desktop → Settings → Accounts on macOS.

In the same window, open Git and check the name and the email that will sign your commits. They are public. If you use a pseudonymous account, put the same pseudonym here.

2. Fork, then clone your fork

Fork. Open the course repository ↗ in the browser and click Fork, at the top right. Keep the proposed name. GitHub creates your-handle/AI4Transcriptomics_AI4OH_2026.

Clone your fork. In GitHub Desktop: File → Clone repository… Pick your fork in the GitHub.com tab, choose a local folder outside any synchronised drive, and click Clone.

GitHub Desktop sees that the repository is a fork and asks how you plan to use it. Choose To contribute to the parent project. Your pull request will then go to the course repository.

Check the name before you clone: it must start with your handle. A clone of the course repository lets you commit, and refuses your first push.

3. Make your first commit

Produce something to commit. In a terminal, inside the practical folder of your clone (Repository → Open in Command Prompt or Open in Terminal, then cd practical):

uv sync
uv run python scripts/step1_fetch_and_audit.py

Back in GitHub Desktop, the Changes tab lists the new and modified files and shows the difference line by line. This view is git status and git diff at once. You should see files under results/step1_audit/.

The checkboxes are git add: tick the files that belong to this commit. Then write the message at the bottom left. Summary is the short first line. Description is the why, or what is left to do. Click Commit to main.

Read the list of files before you commit. Nothing from practical/data/ or practical/doc/ may appear: no data file, no PDF of the paper, no report. The .gitignore of the practical already excludes both folders. If such a file shows up, you saved it in the wrong place: move it, do not commit it.

4. Push to your fork

The commit exists only on your laptop. The top bar now reads Push origin with a counter. Click it: your commit goes to your fork.

5. Open your pull request early

Your pull request is your submission. Open it as soon as you have pushed one commit: each later push to your fork appears in it automatically.

Branch → Create pull request. The browser opens on the form of the course repository. Before you write anything, set the first line:

  • base repository: AI4Health-DAISY-LIG/AI4Transcriptomics_AI4OH_2026
  • base: the branch named after your handle, not main
  • head repository: your fork, compare: main

The description is pre-filled with the template of the course: the four steps to tick, the checks, what you want reviewers to look at, and the help you received and gave. Fill it, then click Create pull request. You edit this description as you progress.

Commits you pushed before you opened the pull request are already in it: see troubleshooting if some seem to be missing.

If the list of base branches does not contain your handle, your branch does not exist yet: check that you sent your handle through the UNESS form, then ask in an Issue. Do not open the pull request against main.

6. Keep working: commit, push

Each time you stop working, commit and push, even if the code is broken. A message such as "to do next time: …" or "having a bug in …" is a good message: your commit history is part of your work.

  1. Look at Changes, tick the files.
  2. Write the summary, click Commit to main.
  3. Click Push origin.

The pull request shows the new commits at once. Its state at the deadline is what is graded. It must contain all your code, your results and your filled worksheets. To see what a past commit changed, open the History tab and select it.

7. Ask and answer in Issues

Questions go to the Issues of the course repository, not to private messages: one issue per question. This is your help trail, and it makes the help you give visible.

Ask. Repository → Create issue on GitHub, or the Issues tab of the course repository → New issue. Choose the question template, the only way to open one. Check that the address bar shows the course repository.

Answer. Open a peer's issue and write in the comment box. Explain, point to documentation, debug together. Do not paste a solution to copy.

Link. Each issue and each pull request has a number. Typing #12 in any comment or description creates a link in both directions. In your pull request, list under "Help I received and gave" the issues where you were helped and those you answered, for example #12, #31. To address someone, type @their-handle.

8. Review a peer's pull request

You review at least one peer's pull request in the week before the final deadline. Open the course repository in the browser, then Pull requests, choose a peer's request and go to Files changed.

  1. Read what the author asks reviewers to look at, in the description.
  2. Hover a line and click + to comment on that line. Ask a question or suggest an improvement.
  3. Click Review changes, write a summary, choose Comment, and submit.
  4. The author answers in the thread and, if needed, commits and pushes a change: the request updates itself.

To run a peer's code before you comment: in GitHub Desktop, Current Branch → Pull requests tab, select the request, and GitHub Desktop checks it out. Come back to main with Current Branch before you work on your own code.

Reviewing is reading, questioning and suggesting. Copying code or text from another student, or letting someone copy yours, is plagiarism under the rules of the course repository.

9. Stay in sync with the course repository

The instructor may update the course repository during the practical, for example to fix a script. Your fork then falls behind. Bring the update in with two moves.

On GitHub. Open your fork in the browser. A line says "This branch is N commits behind". Click Sync fork → Update branch.

On your laptop. In GitHub Desktop, click Fetch origin, then Pull origin when the button changes.

Commit or push your own work before you sync. You can also do it without the browser: Branch → Merge into current branch…, choose upstream/main, then Push origin.

10. Cite your work in the report

Each factual claim of your report links to your code, your results or your worksheets. Two objects make these links stable.

A permalink. On GitHub, open the file in your fork, click the line number, then … → Copy permalink. A permalink contains the hash of a commit, so it still points to the same lines after you push new commits.

The hash of your last commit. The report asks for the commit your results are based on. In GitHub Desktop, open History, right-click the commit and choose Copy SHA.

The report itself stays out of the repository: you submit it as a PDF on UNESS.

11. Troubleshoot with small checks

I committed before I opened the pull request

Nothing to attach. A pull request does not hold a list of commits chosen by hand: it shows each commit that is on the main of your fork and not yet on your branch of the course repository. The commits you made before you opened it are included from the start, and those you push later join it automatically.

Check it: open your pull request on GitHub and click the Commits tab. Your earliest commit should be at the top of the list. If commits are missing, one of three things happened.

  • They are not pushed. In GitHub Desktop the top bar reads Push origin with a counter. Click it, then reload the pull request.
  • They are on another branch. The History tab of main does not show them, and Current Branch lists a second branch. Switch to main, then Branch → Merge into current branch…, choose that branch, and click Push origin.
  • They are in another folder. You first worked in a clone of the course repository, or in a downloaded copy, and cloned your fork later. For a clone of the course repository, follow "The push is refused" below: its commits then go to your fork. For a downloaded copy without Git, copy your files into the clone of your fork and commit them there; the commit will carry today's date.

The push is refused: permission denied

You cloned the course repository instead of your fork. Look at Repository → Repository settings → Remote: the address must contain your handle. Replace it with the address of your fork and push again. Your commits are kept.

My pull request targets main, or my own fork

Open the pull request on GitHub, click Edit next to its title, and change the base branch to the one named after your handle. If the base repository is wrong, close the request and open a new one.

A data file or a PDF appears in Changes

Untick it and move it into practical/data/ or practical/doc/, which git ignores. If you already committed it and have not pushed, History → right-click the commit → Undo commit. If you already pushed, ask in an Issue before you do anything else: a file stays in the history after you delete it.

The pull after a sync shows a conflict

You and the instructor changed the same lines. GitHub Desktop lists the conflicted files and opens them in your editor. Each conflict is marked with <<<<<<<, ======= and >>>>>>>. Keep the lines you want, delete the markers, save, then click Continue merge and push.

GitHub Desktop proposes a force push

Stop and ask. A forced push rewrites the history that your pull request shows and that reviewers have read.

GitHub Desktop with GitLab

The practical sessions use GitHub. For your other projects, GitHub Desktop also works with a repository hosted on GitLab: clone, commit, push, fetch and pull are plain Git.

  • You do not sign in. Create a personal access token on GitLab with the read_repository and write_repository scopes, clone through the URL tab, and give your GitLab username with the token as password.
  • The buttons that open issues and pull requests only know GitHub. On GitLab you do those steps in the browser, where a pull request is called a merge request.
